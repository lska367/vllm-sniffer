# 科研工具平台规划

> vllm-sniffer 的最终定位：**KV Cache 研究的数据采集与分析基础设施**。
> 本文档把研究问题翻译成工具需求，说明三层能力（采集/分析/可视化）
> 如何支撑研究线。研究背景见 `doc/PLAN.md`、`doc/papers/`（研究线目录）。

## 1. 为什么需要自建工具

研究线（KV Cache 优化）依赖对 vLLM 运行时行为的细粒度观测，但：

- vLLM 自带日志是**面向运维**的（错误/警告），不是面向研究的
  （行为级数据：调度决策、KV 块分配、逐 token 延迟）
- vLLM 官方 metrics 是**聚合值**（平均延迟等），粒度到不了
  "某个请求在某个 step 发生了什么"
- 复现实验（temp=0 不确定性、preemption 影响）需要**可对拍的原始事件流**
- 行为不变约束保证**观测本身不污染结论**——这是科研工具的生命线

## 2. 研究问题 → 数据需求映射

| 研究问题 | 需要的数据 | 现有事件 | 缺口 |
|---|---|---|---|
| 前缀缓存命中率与收益 | 每请求命中/未命中、块分配 | schedule（token 数/块分配） | **命中未命中的显式标记**（v1 缓存接口的观测点） |
| 解码瓶颈定位 | 逐 step 耗时分解 | step / forward | **耗时分解**（attention vs MLP、采样 vs 拷贝） |
| temp=0 输出不稳定 | margin 分布、flip 位置、batch 组成 | sample_flip / sample_stats / forward | 位级指纹（P1-1） |
| preemption 代价 | 重算次数、重算耗时、受影响请求 | preempt / schedule | 重算耗时归属（forward 与 preempt 关联） |
| batch 组成影响 | 每步 num_seqs/num_tokens + 性能 | forward | **与 logits 指纹联合分析**（P1-1） |
| KV 块碎片/水位 | 块分配/释放序列 | schedule（new_block_ids_to_zero） | 释放事件、块表水位 |
| 长上下文行为 | TTFT/TPOT 随 context 增长曲线 | request_* | 分段 TTFT（prefill 分块） |

> 设计原则：**先固化"研究问题 → 数据需求"的映射，再决定加不加 hook**。
> 每条新 hook 都要能回答一个具体研究问题，禁止"先采了再说"。

## 3. 平台三层架构

```
┌─ 采集层 vllm-sniffer（已完成 v0.1）─────────────────────┐
│  事件流 JSONL（schema_ver=1，行为不变，<1% 开销）        │
│  → 下一阶段：env_snapshot、位级指纹模式、命中率观测点    │
├─ 分析层 tools/（P0-2 起步）─────────────────────────────┤
│  jsonl→parquet → 延迟分布 → repro 对拍 → flip 归因      │
│  → 下一阶段：warmup 净化、聚合 API（供前端）             │
├─ 可视化层（P2-1）───────────────────────────────────────┤
│  FastAPI 聚合 + 时间线/热图/散点                        │
└──────────────────────────────────────────────────────────┘
```

- **采集层**：只做观测，无状态、无判断（对拍/结论都在分析层）——
  保证同一份原始数据可以支撑多种分析视角，不用重新跑实验
- **分析层**：从"能跑"到"能讲故事"。所有论文数字必须能从
  parquet 复现（可复现性 = 科研底线）
- **可视化层**：把分析结果变成可检查的图形（审稿/答辩材料）

## 4. 与研究的衔接方式

### 4.1 实验工作流

```
1. 定义研究问题 → 2. 确定需要的事件（查 EVENT_SCHEMA.md，缺则加）
3. 跑实验（.venv-gpu 真机，scripts/ 冒烟先行）
4. 导出 parquet → 5. 分析/画图 → 6. 结论写入 daily log / 论文
```

每个实验 = 一个 run_id，run_id 目录自含全部原始数据 + env_snapshot
（P0-1 后），**原始数据永不改动**（分析只读 parquet，坏了重导出）。

### 4.2 与现有研究资产的关系

- `doc/PLAN.md`（研究时间线）：工具建设排入 9 月入学后的 GPU 部署阶段
- `doc/papers/`（49 篇论文，13 篇核心）：读论文时把"需要什么数据验证
  这个 claim"记入 doc/README 的论文笔记，反向驱动 hook 设计
- 毕业目标（FAST/SOSP 2027）：工具支撑 1-2 个实验章节；
  temp=0 不确定性的量化观测（19/64 flips）已是可讲的故事素材

### 4.3 工具本身的产出物（可复用）

- **temp=0 不确定性证据包**：V100 上 0.5B 模型 64 token 输出 19 个
  flip 区位置的完整数据（2026-08-06 真实记录）
- **延迟基准包**：TTFT/TPOT 分布脚本，任何模型/环境一键出报告
- **可复现实验模板**：同 prompt N 连发 + flip 密度（P1-2）

## 5. 平台化里程碑

| 阶段 | 标志 | 依赖 |
|---|---|---|
| M1 采集可用 | 7 事件 + 真机验证（✅ v0.1） | — |
| M2 分析可用 | parquet 导出 + 延迟报告 + 对拍（P0-2） | — |
| M3 归因可用 | env_snapshot + 位级指纹 + 复现实验（P0-1, P1-1, P1-2） | GPU 环境 |
| M4 平台化 | 可视化前端 + 聚合 API（P2-1） | M2 |
| M5 规模 | TP/PP/Ray + OTLP（P2-2, P2-3） | 多卡环境 |

## 6. 质量底线（科研工具的红线）

1. **观测不改行为**：任何 hook 不得影响推理结果（回归测试：开/关
   tracer 各跑一次，输出必须逐 token 一致——应固化为 CI 步骤）
2. **数据可复现**：同 run 同结论；分析脚本固定 seed、固定输入
3. **开销可声明**：每新增一个 GPU 观测点，实测并记录开销增量
4. **隐私默认**：prompt 内容永不落盘
